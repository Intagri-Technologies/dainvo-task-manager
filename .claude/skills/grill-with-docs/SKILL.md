# Grill With Docs

Use the `grilling` skill and the `domain-modeling` skill together: `grilling`
runs the interview, `domain-modeling` captures what it settles.

That pairing is the whole point. An interview that ends in a shared
understanding and no artifact leaves the next session to rediscover it — which
is the gap in this workspace's existing plan documents. `CLICKUP_PLAN.md`,
`MONDAY_PLAN.md`, and `RULES_ENGINE_PLAN.md` were all authored plan-first
before any implementation, and each records what was decided but not the
alternatives that were rejected or why. This skill closes that.

## When it is worth it

An interview loop spends tokens up front to avoid building the wrong thing.
Be honest about the trade rather than reaching for it reflexively:

- **Worth it**: a new provider integration, a subsystem like the rules engine,
  a migration, anything spanning more than one session or repo. Misalignment
  there costs far more than the interview.
- **Not worth it**: a bug fix, a copy change, a one-file refactor. Ask the one
  question you actually have and get on with it.

If you are unsure which side a task falls on, say so and let the user decide
before spending the rounds.

## As you go

**Glossary entries, the moment a term is settled.** When the interview pins
down what a word means, `domain-modeling` writes it into the owning project's
`CONTEXT.md` right then — not batched at the end, where it gets lost. If the
term crosses projects, `CONTEXT-MAP.md` records the crossing.

**ADRs, sparingly.** Offer one only when all three hold: the decision is hard
to reverse, it would surprise a future reader, and it came from a real
trade-off with genuine alternatives. Use the format in the `domain-modeling`
skill's `ADR-FORMAT.md`; ADRs live in the owning project's `docs/adr/`. The
value is recording _why_, including the alternatives you rejected — precisely
what the existing plan docs omit.

Do not put ADRs under `dainvo/docs/` or `dainvo-docs/docs/`: both trees are
published. For those two projects, and for decisions spanning repos, write to
`docs/adr/` at the workspace root.

## Where it leads

Nothing here executes the plan. When the frontier is empty and the user
confirms shared understanding, the output is a sharpened design plus its
glossary entries and any ADRs.

If the effort turns out to be larger than one session can hold, that is the
signal to reach for the `wayfinder` skill and chart it as a map of decision
tickets instead — `grill-with-docs` is then how individual grilling tickets on
that map get resolved.
